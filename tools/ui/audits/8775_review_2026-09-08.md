# 8775 AI 结果人工质检工具审查

审查日期：2026-09-08。范围：在线 v39 的实际入口与完整继承/前端补丁链，多人标注、视频读取及高延迟网络下的可靠性。交付为统一管理入口、文档和诊断脚本；本次未修改服务实现、重启在线进程、改变账号分配或写入生产标注数据库。

## 结论

现有设计具备小团队分视频标注的基础：唯一视频分配、服务端权限检查、revision 冲突拒绝、SQLite WAL、后台顺序保存和局部响应。但不能据此认定高并发/弱网使用已可靠。已复现三个直接影响流程或数据正确性的问题：HTTP/1.1 登录重定向读取超时、保存失败后数据库仍已提交、视频请求乱序导致选择与内容错配。前端队列缺少持久化与幂等重试，也会放大弱网风险。

在线配置的 faststart 目录没有可用文件，实际回退的 148 个视频有 147 个 moov 索引在 mdat 后。当前传输是完整 MP4 的按字节 Range 读取，不是实时流或自适应码率。原码率、额外索引请求、无优先级的共享带宽及数据库认证写入会共同影响多人跳转体验。**先修复可靠性问题与媒体准备，再进行容量验收；不要直接增加多个 Python worker 共享初审库。**

## P1：HTTP/1.1 重定向没有响应结束边界

证据位置：`tools/football_event_review/server_multiuser_v37.py:180` 开启 HTTP/1.1；`server_multiuser_v30.py:490` 的已登录入口、`:499` 注销及 `:548` 登录成功分支发送 302，却未设置 `Content-Length: 0` 或关闭连接。

对 v39 实际 Handler 的隔离服务，已登录入口和登录 POST 均收到 302，但响应体读取超过客户端 0.5 秒超时；同服务 `/healthz` 正常读取。某些浏览器可能提前处理 Location，因此不能说所有浏览器必然卡死，但依赖完整响应边界的客户端会等待连接超时。15 秒 socket 空闲超时不应充当响应边界。

建议统一封装空响应/重定向，补齐准确 Content-Length，覆盖登录、退出及已登录入口；验证同连接连续请求与真实浏览器登录。Python 对 HTTP/1.1 持久连接要求准确响应长度，见 [http.server 官方文档](https://docs.python.org/3/library/http.server.html#http.server.BaseHTTPRequestHandler.protocol_version)。

## P1：失败响应不能保证标注回滚

证据位置：`server_multiuser_v30.py:307` 的 `update_segment_for_user`，`server_hierarchical_v15.py:51` 的逐标签更新，`server_multiuser_v36.py:187` 的后置 field_side 校验。外层 RLock 只串行化线程，不形成数据库事务；内层多次 connect 各自提交，审计又是独立事务。

复现：对未审核 shot 提交合法标签和非法 `attribution_by_label.shot.field_side`。逻辑抛出 `Invalid field side: INVALID`，但状态已从 `unreviewed/revision=0` 变为 `accepted/revision=1`。隔离正常单标签保存观测到 **5 次 COMMIT**。数据提交后若审计失败或网络断开，也可能出现客户端认为失败、数据库实际上成功。

建议先验证全部字段，将 revision 比较、插入标签、全部 review 更新、history 和 submission audit 放入同一事务。使用带 revision 条件的 SQL 更新并检查影响行数，保证多进程也在事务层协调。客户端生成稳定 operation ID，同 ID 重试返回既有结果，并校验请求体一致性。当前服务器随机生成的 request_id 是审计标识，不提供幂等性。

验收：非法后置字段、第二标签异常、审计写失败均不改变任何标注；提交后丢响应的重试不重复增加 revision。Undo 也需要相同契约：当前 `/undo` 未接收 expected revision，v36 又将 field_side 恢复放在单独事务，并发保护不完整。

## P1：后台保存队列没有弱网恢复保障

证据位置：`server_hierarchical_v20.py:39`、`server_multiuser_v31.py:122` 生成的保存函数及 `static/app.js:14` 的 api，在最终 v39 JS 中仍生效。

界面先本地标记并跳到下一条，再串行执行 Promise 队列。最终 JS 没有应用级请求超时、AbortController、待发送操作的 IndexedDB 持久化或 beforeunload 待提交提示。请求长期不结束时后续保存受队首阻塞；关页/刷新会丢失尚未发出的内存任务。失败时只恢复当前匹配视频的页面状态，无法证明服务端回滚。这是生效代码审查，未宣称已在真实浏览器完成断网/关页实验。

建议持久化待发送操作，展示待发送、发送中、已落库、冲突、失败状态与数量；增加有界超时、退避和重新登录后的恢复。必须先落实服务端幂等，再启用自动重试。409 应重新读取最新片段并保留本地编辑供处理。不要用 sendBeacon 代替持久确认机制；同片段连续编辑还要避免提前固化前一次保存确认前的旧 expected revisions。

## P1：快速切换视频，旧响应覆盖新选择

证据位置：`static/app.js:291` 的 loadVideo；v37/v38/v39 修改播放方式，但仍保留 `state.currentVideoId = videoId; state.video = await api(...)`，没有请求序号保护。

对最终生成函数用 DOM stub 控制响应顺序：选择 A 再选择 B，先返回 B 后返回 A，得到 `currentVideoId=B`、`state.video.video_id=A`、`mediaBaseUrl=/media/A`。这不是浏览器解码测试，但执行的是当前实际函数，确定性证明状态竞态。一个账号拥有多个视频时，后端权限检查不能识别这种同账号内的画面与选择错配，见 [前端诊断](8775_frontend_2026-09-08.json)。

建议每次加载使用递增 generation，仅最新请求可以更新 state、播放器和事件列表；取消旧 fetch 作为补充。数据确认前禁止对混合状态提交。已有 pendingAbsoluteSeek.videoId 只保护 seek 回调，不能阻止 API 旧响应覆盖。

## P2：视频认证写 SQLite，与标注争抢写锁

证据位置：`server_multiuser_v30.py:194` 的 session_user、`:485` GET 权限检查、`server.py:67` 的连接配置。每次已认证视频 Range、静态文件或 API 请求都会查询会话并 UPDATE last_seen_at，部分路径还会多次检查 current_user。隔离观测 **10 次会话查询产生 10 次写入**。

连接锁等待超时为 30 秒；标注还共用进程内 RLock。WAL 支持读写并行，但同库只允许一个 writer，见 [SQLite 官方并发说明](https://www.sqlite.org/wal.html#concurrency)。因此视频认证会与保存竞争写锁。建议会话验证改为读路径，将 last_seen 更新按会话节流到 30–60 秒并独立处理，不让心跳写失败阻断已验证媒体请求；同时保持过期、注销及分配变化即时或明确有界生效。

进一步按 segment ID 建索引并只读当前片段，减少连接建立、重复 PRAGMA、全视频 JSON 解析及零散 COMMIT。即便 compact response 只返回一个片段，v15/v36 仍多次读取整个视频事件，较大的单视频队列会增加持锁时间。

当前广泛使用 `with self.connect()`，sqlite3 连接上下文只管理提交/回滚，不显式关闭连接。本次已有测试在 Python 3.13 输出 unclosed database ResourceWarning，建议显式 closing/finally close，不依赖 GC。参见 [sqlite3 连接上下文说明](https://docs.python.org/3/library/sqlite3.html#how-to-use-the-connection-context-manager)。

## P2：faststart 媒体未就绪，原码率没有带宽兜底

证据位置：`server_multiuser_v32.py:38` 的媒体选择、`server_multiuser_v37.py:187` 的发送逻辑及 `scripts/watch_remaining148_review_v39_service.py:55` 的部署参数。

在线优先目录没有可用文件，148 个视频全部回退，147 个源文件的索引在文件尾。浏览器通常需额外尾部 Range 获取索引再定位时间。URL 的 `#t=` fragment 不发送到 HTTP 服务器，不代表服务端按时间切片。

v39 的生效发送逻辑是 **64 MiB Range 上限、512 KiB 循环读取、HTTP/1.1 keep-alive、无应用级限速**；v35 的 12 MiB/s 常量已不控制 send_media。无 Range 请求仍返回整文件，不受 64 MiB 上限限制。64 MiB 是响应范围上限，不是浏览器必须下载量或固定缓冲时长。

已有优点：按需读文件、无在线转码、断连结束写入；延迟 TLS 握手和 15 秒 socket 空闲超时避免单个慢连接阻塞 accept。局限：没有媒体公平调度、API 带宽预留、全局活跃连接上限或自适应码率。内核背压不保证不同客户端和标注 API 的公平延迟；慢/空闲 HTTP/1.1 连接仍占线程，backlog 128 不是线程上限。

建议先离线准备 faststart 副本并验证覆盖全部视频；重封装保留画质但约需额外一份媒体容量，当前约 296 GiB，只是容量估算，准备前核实磁盘余量与共享负载。弱网另准备受控低码率版本、提供原画质切换，验证远景小球、颜色和运动细节。不要在用户点击时转码。faststart 不降低码率，也不缩短 GOP。

进一步可将媒体 Range/TLS/连接限额交给 Nginx 等专用服务，使用内部重定向或短期签名 URL 维持鉴权，不把私有视频目录变为公开静态目录。HTTP/2 不增加可用带宽；HLS/DASH 涉及切片、GOP、播放器和画质要求，需混合负载验证后选型。

### 带宽与时延预算

先按 `同播人数 × 每路码率 × 预留系数` 估算容量。系数 1.3–1.5 是规划余量，不是实测结果。例如 4 路均接近本次最高文件平均码率 23.31 Mbps 时，仅媒体平均需求为 93.24 Mbps，加 30% 余量约 121.2 Mbps；瞬时峰值、倍速和 seek 废弃下载还会增加需求，100 Mbps 可用出口不足以保证这一场景。中位码率不能代表所有视频。

首帧/跳转延迟分为 `连接/TLS + 鉴权排队 + 索引/关键帧 Range 往返 + 有用字节传输 + 解码/渲染`。假设需要 1 MiB 有用数据，10 Mbps 有效吞吐下纯传输约 0.84 秒，再加实际串行往返和解码。moov 后置可能增加往返，长 GOP 增加从关键帧解码距离。本次未测 GOP、RTT、丢包与可用出口，不能承诺支持 N 人或首帧 X 秒。

## P2：守护不能识别存活但不可用的服务

证据位置：`scripts/watch_remaining148_review_v39_service.py:117` 起的主循环。启动时 wait_health，循环内检查 tmux 是否存在并周期备份；服务卡住但 tmux 存在时不会因持续健康失败自动重启。READY.json 的更新时间不能证明视频可用或保存成功，本次健康正常但媒体优先目录为空就是覆盖不足。

建议区分 liveness/readiness，周期检测轻量只读 DB 查询与媒体覆盖率；另用隔离数据做端到端保存探测。增加 API 耗时/大小、锁等待、保存队列长度、409/5xx、连接/线程数及媒体 first-byte 观测。重启设置连续失败阈值和退避，避免把一次慢盘误判为崩溃。

## P3：Range 与缓存边界需补齐

普通 `bytes=100-199` 返回正确 206/100 字节，越界起点返回 416 和 `Content-Range: bytes */size`，跨用户视频返回 403，隔离验证通过。但 `bytes=-0` 被 `max(1, int(raw_end))` 转成最后 1 字节并返回 206，错误接受零长度后缀，范围可满足性见 [RFC 9110 §14.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.1.2)。发送 ETag/Last-Modified，但没有实现 If-Range、条件请求或 HEAD。

建议补齐零后缀、空文件、If-Range 不匹配等契约，并在播放器中验证缓存行为。替换同 URL 媒体时使用内容版本化 URL；固定 `stream=original-faststart-v1` 不能标识每次文件更新，避免混用不同文件版本的缓存 Range。

## 实施顺序与验收计划

1. 修复 302 边界、视频 generation 防护、事务与幂等，再实现持久保存队列和状态提示。先验证不丢标、不串视频。
2. 节流会话写入、显式关闭 DB 连接、片段索引/局部查询，准备并验证 faststart 媒体及可选低码率版本。
3. staging 使用接近生产规模和码率分布的数据做浏览器混合负载，再决定媒体服务或数据库架构是否需调整。不要直接使用多个进程共享现有初审库扩大并发。

建议矩阵：1/4/8/16 标注客户端，持续播放、每 5–15 秒随机 seek、每 2–5 秒保存、多标签编辑、快速切换视频；RTT 20/80/150/300 ms，吞吐 5/10/30 Mbps，丢包 0/1%，另测保存断网后恢复与关页重开。每档至少 10 分钟。在隔离客户端代理或浏览器工具施加网络条件，不修改共享生产网卡 tc。这些是**尚未执行的验收计划**。

| 指标 | 建议目标（待按使用场景确认） |
| --- | --- |
| 数据正确性 | 0 次丢标、重复应用或跨视频错配；冲突可恢复 |
| 保存响应 | RTT ≤80 ms 且带宽满足媒体预算时，P95 ≤500 ms、P99 ≤1 s |
| 已缓冲跳转 | P95 ≤300 ms |
| 未缓冲跳转/首帧 | 同上述网络条件，P95 ≤2 s，冷/热连接分开报告 |
| 播放停顿 | 稳定播放阶段停顿时长占比 <1%；码率超过链路容量的情况独立归类 |
| 待保存队列 | 可见、可恢复、有上限，不无限增长并继续显示成功 |

整视频独占分配避免不同账号互相覆盖，但不按候选数量/难度平衡负载，也没有动态任务租约或多人独立复标汇聚。合成测试中同 revision 两线程保存恰好一成功一冲突，仅证明当前单进程保护，不证明多进程安全。
