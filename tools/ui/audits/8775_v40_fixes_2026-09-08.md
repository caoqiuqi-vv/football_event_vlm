## 服务端事务与接口

实现位于 `tools/football_event_review/reliable_store.py`、`server_multiuser_v40.py`。

三个写接口均要求前端提供长度 8–128 的稳定 operation_id：

- `POST /api/events/{id}/segment-decision`：同时带 expected_revisions。
- `POST /api/events/{id}/undo`：同时带 expected_revision。
- `POST /api/videos/{id}/team-profile`：同时带 expected_revision。

成功响应包括 operation_id；相同账号、相同 ID 和请求体重试返回已提交回执，不再次修改数据。相同 ID 携带不同内容返回 409。权限在回执返回前检查；没有权限的账号不能重放其他视频操作。已提交回执先于可变业务状态校验读取，避免数据变化使合法重试失去幂等性。

新增三张表：`review_operations`、`review_metadata`、`review_segment_index`。业务更新、审计和成功回执一起提交，失败一起回滚。BEGIN IMMEDIATE 在 SQLite 层协调不同 Store 实例；不是仅依靠 Python RLock。两实例同 revision 并发已验证一成功一冲突，重复 operation_id 并发返回相同结果。当前生产配置仍为单进程多线程，未把单项正确性测试等同于多 worker 容量验收。

在生产数据库私有备份上执行初始化，`reviews`、`review_history`、`video_team_profiles`、`video_team_profile_history` 和 `submission_audit` 的逐表指纹保持相同。升级会创建索引和元数据，不重写人工结论。

## 前端弱网流程

实现位于 `static/review_outbox.js` 和 `static/reliable_review.js`，在全部历史补丁之后接入，保留原 GT 删除播放确认保护。

每条操作同步写入独立 localStorage 键后才改变本地审核状态或导航。键包含数据库 namespace、账号和 operation ID；刷新/重开后恢复。相同片段在未完成发送时不接受覆盖式编辑。队列最多 100 条，网络失败以相同 ID 退避重试，最长间隔 10 秒；其他片段不被已明确失败的操作永久阻塞。

401 暂停并提示重新登录；400/409 等明确失败保留草稿。用户可以读取最新数据、恢复原草稿并核对后重新提交，也可明确放弃这条失败草稿。存储满时拒绝操作，不误标为已审核。队列未清空时关页会提示。视频加载/播放器失败可在页面重试。

队列只属于同一浏览器、同一站点与账号；清除站点数据或换浏览器不会迁移草稿。localStorage 的持久恢复针对页面刷新和网络故障，不宣称覆盖磁盘损坏或用户主动清除数据。

## 媒体准备与部署

新媒体目录为：

```text
outputs/football_full_review/full166_fromlast_e8_best_dense_s5_20260902/
  review_platform_remaining148/media_faststart_v40/
```

准备命令：

```bash
python tools/football_event_review/build_original_faststart_streams.py \
  --manifest <review_manifest.json> \
  --output-dir <media_faststart_v40> --jobs 1
```

使用 `ffmpeg -c copy` 保持原编码画质，将 moov 移到 mdat 前；不重新编码，不改变源文件。输出与源文件身份匹配后才跳过，已有不同源文件的缓存不能直接复用。独占准备锁防止两个生成器同时写同目录；单文件写入前检查源文件大小加 5 GiB 磁盘余量，完成后校验并 fsync，再原子替换；中断可重跑。批量准备使用 nice/ionice 低优先级。

服务的媒体 URL 包含基于路径、mtime 和大小的版本；打开后的传输以该文件描述符的元数据校验版本，避免原子替换时混用新旧文件。8 MiB 是单次 Range 的响应上限，不是带宽限速或必须完整下载量。原码率保持不变，faststart 也不缩短 GOP；低于视频实际码率的网络仍可能卡顿，本次没有通过有损压缩换取性能。

`/healthz` 检查版本与存活，`/readyz` 检查数据库元数据和实际媒体 faststart 覆盖；未就绪返回 503。`--require-faststart` 可拒绝媒体不完整时启动。

固定任务的发布与守护脚本为 `scripts/watch_remaining148_review_v40_service.py --activate`。脚本先确认全部媒体已就绪、监听进程身份及最近 60 秒没有活跃审核会话，再停止对应旧 watcher，对数据库进行切换前与旧服务停止后的两次备份，启动 v40。之后每 30 秒检测，连续三次失败重启，每 10 分钟备份，并更新 READY.json / READY_v40.json。

切换后已有页面需要刷新，以载入新保存协议。旧前端没有 operation_id，v40 会拒绝旧提交并提示刷新，避免绕过幂等保护。回退时应先停止 v40 watcher/服务，再恢复旧入口；新增元数据表不要求删除，保留完整数据库及备份，不直接将旧主文件覆盖到活跃 WAL 数据库上。

## 验证结果

- 18 个后端回归：回滚、幂等、双实例并发、局部片段保存、只读认证、连接关闭、撤销、队伍设置、混合媒体与写入、HEAD/Range、请求大小与时间边界、TLS 慢握手隔离。
- 5 个保存队列测试：刷新恢复、409 草稿、存储配额、账号/任务隔离、有界队列与失败隔离。
- 3 个既有队伍标注测试通过；其旧 v36 实现仍输出原有连接 ResourceWarning，v40 已有显式关闭连接的专项通过测试。
- Chromium 场景：登录、MP4 播放、离线后刷新恢复、提交后丢响应的幂等重试、视频响应乱序、存储配额失败、原 GT 删除保护、409 后草稿恢复并重新提交。页面 JavaScript 错误为 0。
- 当前测试 Chromium 没有 H.264 解码器，因此播放测试使用 VP9/MP4 合成视频；它验证服务传输与播放器交互，不等于实际用户浏览器的全部 H.264 视频兼容性验收。
- 生产数据库备份迁移的五张标注/历史/审计表指纹不变。
- 使用临时目录、模拟健康请求检查守护循环：连续三次就绪失败触发一次重启，不影响生产服务。
