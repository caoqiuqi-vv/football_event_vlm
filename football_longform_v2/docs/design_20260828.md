# Football LongForm V2：连续时间轴、层级事件图与候选精查

日期：2026-08-28  
状态：新链路设计基线；与 `train_football_events.py` 旧链路隔离

## 1. 决策摘要

新链路不再把“10 秒窗口是否包含事件”作为主任务，而把完整长视频表示为一条只计算一次的连续时间轴：

```text
long video
    │
    ├── 低频场景/语义特征（DINOv3，1–2 fps，一次性缓存）
    ├── 高频全帧运动特征（轻量RGB视频编码器，8–12 fps）
    ├── 音频与质量元数据（可选）
    └── 检测/轨迹特征（默认关闭，仅训练特权辅助）
                    │
                    ▼
       多尺度连续时序定位器（60–120 秒上下文）
                    │
       ┌────────────┼──────────────┐
       ▼            ▼              ▼
   shot proposals  restart proposals  generic/OOD proposals
       │            │
       ▼            ▼
 shot/save 精查器   set-piece 子类型精查器
       │            │
       └──────┬─────┘
              ▼
      事件关系图 + PointNMS
              ▼
 shot / save / corner / penalty / freekick / kickoff
```

核心变化：

1. 全视频只构建一次特征时间轴，不再重复解码重叠窗口。
2. 主定位器输出每个时间点的事件峰值和偏移，不输出 clip 标签。
3. 六类不是平铺建模，而是 `shot chain` 与 `restart family` 两个事件族。
4. `save` 建模为 `P(shot-chain) × P(save | shot, future context)`。
5. `corner/penalty/freekick/kickoff` 建模为 `P(restart) × P(subtype | restart)`。
6. 候选生成和候选精查严格分开，各自有独立的召回上限与成本指标。
7. RGB-only 是唯一主链和选模口径；检测/轨迹缺失不得阻断 proposal 或最终预测。

## 2. 为什么停止继续扩展旧主线

当前工程已经给出足够的反证，说明继续修改同一个 10 秒窗口分类器不是高收益路线。

### 2.1 已确认的失败证据

- 当前输入 `24 frames / 10 s = 2.4 fps`，射门到门将干预常只覆盖 1–2 帧。
- 最新 Online-Val15 的高召回工作点约为：
  - shot：`P@R85 = 0.281`
  - save：`P@R80 = 0.077`
  - set_piece：`P@R80 = 0.118`
- proposal/candidate ceiling 仍约为 0.96–0.97，说明主要问题是候选判别而不是完全找不到候选。
- save/set-piece 的高分 FP 多数离任意 GT 很远，并且是持续背景高分，不是孤立毛刺。
- dense hard-negative 已真实参与训练，但没有改善 shot/save；继续增加同类负样本不是主要解法。
- 邻窗平滑、最大值融合等 12 种后处理均退化。
- train-score 时序重评分没有跨视频泛化；未来所有二阶段模型必须使用 video-level OOF 候选训练。
- 检测证据真实接入后只有温和变化，说明 presence/简单几何不能替代正确的时序任务定义。
- 已有 VideoMAEv2 实验 mAP 约 0.33–0.36；单纯更换视频 backbone 不是充分条件。

### 2.2 旧链路中应保留的资产

- 人工修复后的 point annotations 与 label mask。
- 固定外部测试集、PointNMS、one-to-one matching、视频级 bootstrap。
- `football_evidence_provider.py` 的缺失证据回退语义。
- `scripts/build_evidence_index.py` 的轨迹特征仅保留为可选训练特权信息或诊断资产，不作为推理依赖。
- `scripts/build_audio_feature_index.py` 的音频时间轴与 valid mask。
- DINOv3 checkpoint、LoRA 实现和已验证的多层视觉 readout。
- hard-negative/review 工具，但只用于 OOF proposal 产生的真实候选。

### 2.3 不应直接继承的部分

- 不在新链路中继续扩展 `train_football_events.py`。
- 不继承 10 秒 clip BCE 作为主目标。
- 不继承所有类别共享同一个 clip token 的结构。
- 不让阈值、平滑或 per-video calibration 掩盖排序问题。
- 不把镜头边界当作硬视频分割。
- 不用在训练视频上拟合出的 in-sample 分数训练 reranker。

## 3. 数据现实与标签本体

按当前 repair JSON 中“未被明确拒绝”的事件行统计（训练时仍需叠加类别级 label mask）：

| 类别 | train_fit147 | calibration20 | thirdparty18 test |
|---|---:|---:|---:|
| shot | 3272 | 604 | 559 |
| save | 1401 | 188 | 209 |
| corner | 681 | 124 | 80 |
| freekick | 638 | 109 | 106 |
| kickoff | 142 | 138 | 97 |
| penalty | 34 | 0 | 0 |

这带来三个硬约束：

1. penalty 当前不能作为一个可独立验证的普通分类头；校准和外部测试均无正例。
2. restart 四个子类型分布极不平衡，必须先学习共同的 restart 表示。
3. 新切分必须按视频和来源隔离，同时保证六类在 calibration/test 中存在；否则不能声称完成六类识别。

### 3.1 层级标签定义

```text
event
├── shot_chain
│   ├── shot
│   └── save（shot_chain 的结果/响应事件，可与 shot 同时存在）
└── restart
    ├── corner
    ├── freekick
    ├── penalty
    └── kickoff
```

模型内部额外学习非产品输出状态：

- `open_play_attack`
- `stoppage_or_setup`
- `restart_execution`
- `goalkeeper_intervention`
- `other_football_action`
- `unknown_or_low_quality`

这些辅助状态用于分离易混背景，不直接进入最终六类 API。

### 3.2 时间语义

- 保留 repair JSON 中已审核 timestamp 作为最终 spotting anchor。
- raw interval 只作为可选上下文，不使用 midpoint 替换 anchor。
- rejected raw event 作为 ignore zone 或审核队列，不直接作为负例。
- restart 内部可同时预测 `setup onset`、`execution peak`；最终输出仍回归到审核 anchor。

## 4. 模块 A：一次性多速率时间轴

### 4.1 时间轴频率

LF-A0 统一存储为 5 Hz 主时间轴，并为每个模态记录原始时间戳：

| 模态 | 建议频率 | 作用 |
|---|---:|---|
| DINOv3 global/context | 1–2 fps | 球场布局、镜头、人物分布、静态语义 |
| lightweight full-frame RGB motion | 8–12 fps | 全画面运动、群体状态、起脚/扑救反应；主链必需 |
| detection/track evidence | 10–15 Hz，可选 | 仅训练蒸馏、诊断或有界残差；不得控制候选门控 |
| audio | 10 Hz | 哨声、能量起始、观众反应 |
| quality/view/cut | 2–5 Hz | 缺失、模糊、摇镜、视角和切镜置信度 |

所有模态使用显式 `timestamp`、`delta_t`、`valid_mask`，禁止只用 token 序号暗示时间。

### 4.2 特征缓存格式

每个视频生成一个版本化目录：

```text
feature_store_v2/<video_id>/
├── manifest.json
├── timeline.npz
├── dino_2fps.fp16.npy
├── rgb_motion_8hz.fp16.npy
├── evidence_15hz.optional.fp16.npy
├── audio_10hz.fp16.npy
└── quality_5hz.fp16.npy
```

`manifest.json` 必须记录：视频 hash、fps、duration、抽帧索引、backbone hash、代码版本和各模态覆盖率。缓存只能由内容 hash 命中，避免旧特征与新视频静默错配。

### 4.3 采样原则

- 基础低频时间轴永远存在，防止 actionness 漏掉静态定位球。
- 镜头边界只生成 metadata，不截断事件上下文。
- 低分辨率全帧 motion encoder 连续扫描一次；候选区才启用高分辨率 RGB tile/glimpse。
- 检测/轨迹不得参与 proposal 硬门控；缺失时主链输出必须保持定义良好。
- 所有可选模态均显式回退，entity evidence 训练 dropout 不低于 80%。

### 4.4 前置检测解耦原则

新链路的主函数必须是 `score_rgb = f(context_rgb, motion_rgb, timestamps)`。当球在像素空间不可见时，模型仍可依赖间接但稳定的事件证据：群体加速/减速、起脚与身体姿态、守门员反应、攻防阵型变化、摄像机跟随、停赛到重新开球的状态转移。模型不被要求恢复一条物理上不可见的球轨迹。

检测/轨迹只允许两种接入方式：

1. **训练期特权蒸馏**：仅在 evidence valid 的位置，用小权重让 RGB student 学习 teacher 的关系表征；GT loss 永远直接监督 student，teacher 分数不能替代标签。
2. **可关闭有界残差**：`score = score_rgb + clip(delta_entity, -0.15, 0.15)`；不得使用 `ball_detected AND proposal`、ROI-valid gate 或基于检测的候选删除。

候选精查的空间关注由全帧 patch tokens、均匀高分辨率 tiles 与 class event queries 学习得到，不由检测框裁剪。这样检测成功时可以提供增益，检测失败时不会改变系统定义或召回上限。

## 5. 模块 B：连续多尺度事件定位器

### 5.1 推荐结构

采用轻量的 T-DEED 风格 temporal encoder-decoder。主输入是 DINO 场景上下文与全帧 RGB motion token；输入不要求球、球门或球员检测成功，也不是重叠 raw-video clips：

```text
5 Hz aligned features
    ↓ temporal stem
5 Hz ─────────────── skip ─────────────┐
    ↓ stride 2                         │
2.5 Hz ───────────── skip ────────┐    │
    ↓ stride 2                    │    │
1.25 Hz long-context blocks      │    │
    ↓                             │    │
decoder + skip connections ──────┴────┘
    ↓
5 Hz dense point heatmaps + offset + uncertainty
```

建议从 dilated depthwise TCN/SGP-Mixer 开始，不先上全局 Transformer：

- 线性复杂度；
- 60–120 秒感受野容易实现；
- 可流式推理；
- 对当前约 147 个训练视频更不易过拟合。

长视频训练按 60–120 秒 sequence block 读取；block 是内存调度单元，不是独立 clip 分类样本。相邻 block 使用 state/memory 或只在训练时少量 context overlap，最终预测在完整时间轴上拼接一次。

### 5.2 输出头

主定位器只负责高召回：

```text
shot_heatmap[t]
restart_heatmap[t]
generic_eventness[t]
anchor_offset[t]
proposal_quality[t]
```

save 不在这里做无条件全局扫描；它由 shot-chain proposal 和一个低权重 orphan-save proposal 联合产生。

### 5.3 损失

```text
L = L_quality_focal_point
  + 0.5 L_offset
  + 0.2 L_family_contrastive
  + 0.1 L_temporal_consistency
  + 0.1 L_aux_state
```

- point target 使用类别独立 sigma，避免给 restart 强迫单一尖峰形状。
- ignore zone、partial label mask 必须在每个类别独立生效。
- contrastive 使用跨视频正对，不能让同一比赛的重叠时间点主导。
- 背景采样来自完整连续时间轴，而不是固定 1:3 random clip。

## 6. 模块 C：类别条件化候选精查

候选精查器是新链路精度的主要来源。每个 proposal 只精查一次，不对全视频滑窗。

### 6.1 Shot verifier

上下文建议 `[-3 s, +2 s]`：

- 低频 DINO 全局上下文；
- 8–12 fps 轻量全帧 RGB motion branch；
- 候选区的全帧低分辨率视图 + 均匀高分辨率 tiles，由 event query 软选择；
- 可选轨迹只提供训练蒸馏或小幅残差；
- 输出 shot confidence、精确时间 offset、RGB evidence quality。

关键负类必须显式包含传中、解围、长传、门前盘带和摄像机快速跟拍。

### 6.2 Save verifier

save 是关系事件而不是孤立外观类：

```text
P(save_t) = P(shot_chain_a)
          × P(goalkeeper_intervention_t | shot_a, future[0:5s])
```

输入：

- proposal 对应 shot embedding；
- shot 后 0–5 秒全帧高频运动特征；
- shot 到 save 的相对时间编码；
- learned spatial event queries 从全局 patch/tile 中寻找门将反应、倒地、扑挡和攻防群体变化；
- 可选 goal/ball/player geometry，仅在可靠时提供辅助。

保留 `orphan_save` 支路处理 shot 漏标或 shot locator 漏检，但给它独立阈值和较低先验，不能让它重新退化成全局 save 分类器。

### 6.3 Restart verifier

上下文建议 `[-8 s, +6 s]`，使用状态转移而非纯动作强度：

```text
open play → stoppage/setup → restart execution → open play
```

输出：

- restart/not-restart；
- `corner/freekick/penalty/kickoff` subtype；
- setup 与 execution 的时间位置；
- subtype uncertainty。

输入重点：场地布局、球员站位、角区/禁区几何、哨声、运动下降后重新开始。视角分类概率只作为 soft feature，不硬切 expert。

### 6.4 多模态融合

采用小型 gated late fusion：

```python
z = z_visual
z += gate_motion(valid_motion, quality) * proj_motion(x_motion)
z += clamp(gate_entity(valid_entity, quality), max=0.15) * proj_entity(x_entity)
z += gate_audio(valid_audio, quality) * proj_audio(x_audio)
```

每个 gate 必须有：

- 非零且可学习的初始化；
- `requires_grad` 启动断言；
- 首步梯度与参数变化门禁；
- 缺失模态恒等回退测试。

这是从既有 LoRA 和 evidence gate 静默失效中得到的强制工程规则。主 checkpoint 只按 RGB-only 指标选择；entity 分支不能改变 proposal 是否存在，其 logit 残差必须有界。训练和评估必须覆盖 `entity absent`、`entity randomly dropped`、`entity deliberately corrupted` 三种情况。若加入 entity 后正常集提升、但缺失或错误输入导致召回明显下降，则该分支不进入生产。

## 7. 模块 D：事件关系图与最终解码

使用软关系势能，不使用不可恢复的硬规则：

- shot 后 0–5 秒内的 save 获得关系增益；
- 无 shot 的 orphan save 允许保留，但需要更强视觉证据；
- restart subtype 在同一 proposal 上互斥；
- kickoff 可利用比赛开场/进球后重启状态，但不硬依赖比分信息；
- penalty 与随后 shot 建立可选关系；
- cut/blur 只降低定位置信度，不删除事件。

最终解码对六类分别执行 point peak selection，再进行跨类关系重评分与 one-to-one PointNMS。保存每个结果的 evidence trace，便于人工审核和错误归因。

## 8. 训练方案

### Phase 0：数据与协议修复

1. 将用户指定的18个视频冻结为唯一 `thirdparty18` 对齐终审集，禁止用于训练、OOF、早停、阈值选择、融合、校准或消融决策。
2. 保留与它配套的 train_fit147/calibration20，并在 train_fit147 内部建立 video/source-stratified 开发 folds。
3. 为 penalty 补充本域数据；建议最低目标：train ≥ 60、独立 calibration extension ≥ 15、独立 third-party-style test extension ≥ 15。extension 必须来自新增且视频级隔离的数据，不能改动指定 thirdparty18。达不到时只报告 few-shot/prototype 结果，不宣称稳定六类能力。
4. 抽查每类 50–100 个 anchor 的时间语义，特别确认 restart 标的是 setup onset 还是 execution。
5. 建立 label completeness matrix：每个视频 × 每个类别为 complete/partial/unknown。

### Phase 1：冻结特征的连续 locator

- LF-A0 只用 DINO context + 全帧 RGB motion，不使用 detection/track/audio，不训练 DINO backbone。
- 训练 shot/restart/generic proposal heads。
- 目标不是最终 precision，而是最小 proposal budget 下的召回。
- 通过后冻结 locator 版本，生成全数据 proposal manifest。

### Phase 2：video-level OOF candidate set

- 将 train 视频分为 5 folds。
- 每一 fold 的候选只能由未见过该 fold 的 locator 生成。
- 合并得到 OOF proposal dataset；GT附近为正，其余候选经 label mask/ignore zone 过滤。
- verifier/reranker 只在 OOF 候选上训练。

这一步是必要条件。现有 in-sample temporal rescoring 已证明会学习训练视频特有的分数模式，不能外推。

### Phase 3：三个 verifier 独立训练

- shot verifier；
- shot-conditioned save verifier；
- restart + subtype verifier。

共享底层缓存，但不强制共享最后的判别 token。分别报告 AP、positive P10、negative P90、跨视频 bootstrap CI。

### Phase 4：关系图和可选联合微调

只有三个 verifier 单独通过门槛后才训练关系重评分。首版保持 locator 冻结，避免为了 precision 破坏 proposal recall ceiling。

## 9. 评估协议

### 9.1 必报指标

定位：

- per-class AP / mAP at tolerance 1 s、2 s、5 s；
- strict one-to-one PointNMS precision/recall/F1；
- median/p90 timestamp error。

级联：

- proposal recall @ proposals/minute；
- verifier precision @ fixed proposal recall；
- end-to-end precision @ class recall floor；
- candidate ceiling，任何阶段均不得隐藏召回损失。

产品与效率：

- merged review minutes / video hour；
- candidates / video hour；
- real-time factor；
- DINO frames processed / video second；
- GPU-hours for feature build / training / inference。

鲁棒性分组：

- source/video/domain；
- wide/mid/close/unknown view；
- cut count、blur、camera motion quantile；
- modality available/missing；
- detection absent / sparse / deliberately corrupted；
- 远景且球不可见、强变焦、遮挡；
- subtype support；
- long-tail videos and bootstrap CI。

### 9.2 模块验收门槛

首版建议预注册：

| 模块 | 通过门槛 |
|---|---|
| continuous locator | RGB-only 下 shot/restart recall ≥ 97% 且总 proposal ≤ 6/min |
| shot verifier | P@R85 明显高于旧链路并超过视频 bootstrap CI |
| save verifier | P@R80 至少相对提升 50%，shot-chain ceiling 降幅 ≤ 1pp |
| restart verifier | aggregate restart P@R80 提升，corner/freekick 分别不退化 |
| subtype | 每类独立 AP；无正例的 split 明确记为 N/A |
| detection independence | entity完全缺失时召回下降 ≤0.5pp；错误entity输入时下降 ≤1pp |
| efficiency | DINO 等效处理帧数较旧 10s/stride5 至少下降 40% |

这些是阶段 gate，不是最终产品目标。

### 9.3 A0 全量实验后的实证修正（2026-08-28）

原先“总 proposal ≤ 6/min 且 recall ≥ 97%”的假设没有被 A0 支持，不能继续当作已成立前提。135/18 canonical split 上，A0 类别分数本身的跨视频排序失败；但对六类 logit 取最大值后做 0.5 秒 NMS，得到一个可用的高召回共享触发流：

- 18 个 calibration 长视频共 25,233 个候选，平均 `23.816/min`；
- 2 秒一对一候选 recall：shot `93.39%`、save `90.18%`、corner `96.08%`、freekick `95.92%`；
- 3 秒一对一候选 recall：shot `99.40%`、save `99.39%`、corner/freekick `100%`；
- calibration 没有 penalty 正例，因此 penalty 必须报告为 N/A，并以 train-video OOF 单独验证。

结论分成两层，禁止混报：

1. A0 **不是有效类别分类器**，也没有通过低 proposal budget gate；
2. A0 可暂时作为高召回、无检测依赖的触发器，为短 RGB/VideoMAE verifier 提供候选。

后续报告必须同时列出 source candidate ceiling 与 verifier 后实际 recall/precision。只有 verifier 能把约 24/min 显著压缩且不损失目标召回，这条级联链路才算成立。

## 10. 计算成本预估

旧链路 10 秒窗口、5 秒 stride、每窗 24 帧，忽略缓存时约等效 `4.8 DINO frames/s`。

新链路目标：

- coarse DINO：`1–2 frames/s`；
- 每分钟不超过 6 个 proposal；
- 每个 proposal 最多 8–16 个额外 DINO glimpse；
- 高频 motion 使用远小于 ViT-L 的全帧轻量RGB模型，不能依赖轨迹特征。

以 coarse 1 fps、3 proposal/min、每 proposal 12 个 DINO glimpse 估算：

```text
1.0 + 3 × 12 / 60 = 1.6 DINO-equivalent frames/s
```

相对旧链路理论减少约 67%。实际以解码、缓存命中和轻量 motion branch 实测为准，验收只承诺至少降低 40%。

上述是设计目标，不是当前实测。A0 当前共享触发流为 `23.816 proposals/min`；若每个候选独立解码 16 帧，则 verifier 单独需要约：

```text
23.816 × 16 / 60 = 6.35 decoded frames/s
```

这尚未计入 coarse DINO，并且相邻候选窗口高度重叠。因此 A1 首轮只回答“动作表示能否恢复跨视频 precision”；若有效，工程化必须改为一次顺序解码、共享帧缓存/特征缓存和候选批处理，再实测 RTF。若 A1 无效，则不投入该缓存优化。

## 11. 外部数据与预训练

可使用 SoccerNet Action Spotting / Ball Action Spotting 做 temporal pretraining，重点迁移：

- shot/free-kick/corner/kick-off/penalty 的事件族结构；
- 多尺度 point spotting；
- restart subtype prototype。

不能直接迁移最终阈值，因为广播足球与当前 XbotGo/非标准视角有显著域差异。建议先预训练 locator 与 subtype embedding，再用本域数据完整校准。

研究参考：

- [SoccerNet Action Spotting](https://www.soccer-net.org/tasks/action-spotting)：完整比赛上的稀疏 point event 定义和 17 类基准。
- [E2E-Spot, ECCV 2022](https://www.ecva.net/papers/eccv_2022/papers_ECCV/papers/136950033.pdf)：强调全局动作理解与局部精确时间判别同时存在。
- [T-DEED, CVPRW 2024](https://openaccess.thecvf.com/content/CVPR2024W/CVsports/papers/Xarles_T-DEED_Temporal-Discriminability_Enhancer_Encoder-Decoder_for_Precise_Event_Spotting_in_Sports_CVPRW_2024_paper.pdf)：多尺度 encoder-decoder 与高时间分辨率输出。
- [Precise Event Spotting, CVPR 2025](https://openaccess.thecvf.com/content/CVPR2025/html/Santra_Precise_Event_Spotting_in_Sports_Videos_Solving_Long-Range_Dependency_and_CVPR_2025_paper.html)：长程依赖与类别不平衡。
- [TALLFormer, ECCV 2022](https://www.ecva.net/papers/eccv_2022/papers_ECCV/html/1084_ECCV_2022_paper.php)：缓存/长记忆减少冗余视频 backbone 计算。
- [ActionFormer, ECCV 2022](https://www.ecva.net/papers/eccv_2022/papers_ECCV/papers/136640485.pdf)：无预定义 anchor window 的多尺度连续定位思想；本项目只借鉴时间金字塔，不照搬 interval regression。

## 13. 首轮实验矩阵

只运行能回答架构问题的四个实验：

| ID | 变量 | 目的 |
|---|---|---|
| LF-A0 | DINO 2fps + 全帧RGB motion 8fps | 建立完全无检测依赖的非滑窗 proposal baseline |
| LF-A1 | A0 + audio/quality | 验证非检测可选信息是否提高 proposal recall/budget |
| LF-A2 | A1 + entity privileged distillation | 只验证训练特权信息；生产推理仍为RGB-only |
| LF-B0 | OOF shot verifier | 验证新候选分布下 shot precision |
| LF-C0 | OOF restart hierarchy | 验证 set_piece 合并训练、子类型判别是否成立 |

save verifier 在 LF-B0 shot-chain ceiling 通过后启动。penalty 在补齐 calibration/test 正例前不参与主 KPI。

## 14. Go / No-Go 决策

### Go

- source candidate ceiling 达到目标 recall，且 verifier 后仍满足 shot ≥90%、其他有支持类别 ≥85%；
- OOF verifier 明显改善跨视频 precision；
- 计算量和人工参与时间形成优于旧链路的 Pareto frontier。

### No-Go / 调整

- locator ceiling 不足：提高基础时间轴频率或加入轻量 motion，不先扩大 verifier。
- 只能在约 24/min 达到 ceiling、verifier 又无法显著压缩：判定当前级联不具备产品价值，转向一次顺序解码的连续动作表征，而不是继续做 hard-negative mining。
- locator ceiling 高但 verifier 仍低：问题在标签本体或输入证据，优先做 badcase taxonomy 与数据补标。
- train OOF 好、calibration 差：域不变性失败，停止扩模型，转为 source/view-balanced data acquisition。
- penalty 无法补数据：将它标为 beta/few-shot 能力，禁止与其他五类共同报告一个平均指标。

## 15. 第一阶段交付定义

第一阶段不是训练最终六类大模型，而是交付以下可验证闭环：

1. 一个视频生成一次版本化连续特征时间轴；
2. 连续 locator 对完整视频输出 shot/restart proposal；
3. 严格协议报告 recall@proposal budget、RTF 和 DINO 帧数；
4. 5-fold OOF proposal manifest 可被 verifier 训练读取；
5. 与旧 E20b 在同一 calibration20/thirdparty18 协议下对照。

只有这一闭环通过，才值得投入高帧率 shot/save verifier 和 restart subtype 分支。
